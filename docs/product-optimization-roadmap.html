诊断总结：为什么现在像玩具

四类问题叠加：链路随时会断、断了不知道为什么、也不知道下一步做什么

项目骨架并不差——后端有 checkpoint、幂等的 task_operations 操作表、启动恢复与超时检测；前端有乐观锁保存、逐段重试按钮。但以下问题让它停留在"玩具"层面：

P0 ① 失败/重试链路存在真实的死胡同

用户看到的症状根因
任务永远卡在"素材未齐全"，重试按钮却说"没有需要重试的素材"stale 素材被健康检查算作缺失，却被 _workspace_recovery_targets()（routes.py:1949）跳过
full 模式任务失败后没有任何恢复入口_reconcile_workspace_state()（routes.py:1962）对非 review_first 任务提前 return
"正在生成完整视频预览"永远转圈预览轮询的 catch 直接杀掉 interval，无提示（WorkspacePage.jsx:317）
后端挂了，界面看起来"冻结但健康"工作台 quiet 轮询吞掉所有错误（WorkspacePage.jsx:295）
只有一句"LLM API 调用失败"，无法自救generator.py:99 把真实错误（401/429/超时）脱敏丢弃
50 段里 1 段提示词失败，整个任务停摆task_executor.py:1235 任一失败即整体 halt
finalize 失败可无限原地重复task_executor.py:914 失败后原样放回 awaiting_finalization
上传失败但界面显示成功Upload 失败降级为 warning，状态仍 completed（task_executor.py:1400）

P1 ② 用户引导几乎为零

  • 无阶段说明：用户不知道"预案 → 确认音色 → 确认画面 → 生成素材"每步在干嘛、要多久。
  • 创建任务前不检查 API 配置——等任务失败才发现要先配 key。
  • 最复杂的工作台页面零 tooltip；术语混乱（预案/生产预案/内容预案、项目/任务/草稿混用）。
  • "受众人群"下拉框是纯装饰（ManuscriptPage.jsx:224，不接状态、不上送 API）。

P1 ③ UI"AI 味"的来源是没有设计系统

  • CSS 中 172 种硬编码颜色，全项目仅 9 处 CSS 变量。
  • 讽刺的是：完整的 token 文件 apple-design.css（466 行）是死代码。
  • 工作台单屏塞下 6 个区块，层级扁平、密度过高。
  • 素材生成阶段没有总体进度/ETA；唯一会算全局进度的 TaskProgress.jsx 也是死代码。

基建 ④ 技术债拖慢一切改造

  • WorkspacePage.jsx 928 行巨石组件（20+ useState、单行 JSX 超 600 字符）。
  • 约 1000 行死代码：3 个死页面、TaskProgress、usePolling、format.js 等。
  • 三套各自为政的轮询实现，最完善的 usePolling 没被任何页面使用。
  • 前端零组件/渲染/E2E 测试（13 个测试文件只覆盖纯函数）。

Phase 1 · 可靠性：修死胡同 P0

目标：任何任务在任何失败点都有"看得懂的原因 + 点得动的出路"

R1stale 素材死锁

修法将 stale 纳入 recovery targets；retry-assets scope=failed 同时接受 stale；保证"更新受影响素材"按钮与 recovery 通路一致。

验收stale-only 任务 → recovery.allowed=true，一键重试后 assets_complete=true；补 pytest。

R2full 模式 failed 任务无恢复入口

修法让 full 模式同样经过 _workspace_recovery() 推导恢复动作；保证 can_resume=true 时前端始终渲染恢复按钮（workspacePreview.js:43）。

验收full 模式任务人为 fail → 出现可用恢复按钮并能续跑。

R3结构化错误模型（贯穿前后端）

定义分类：auth / rate_limit / timeout / provider_error / network / disk / config_missing / unknown。各错误字段旁增 *_error_code 列（走既有 _apply_column_migration）；generator.py 等在脱敏 key 的前提下保留状态码与分类；前端按分类映射可行动文案（auth →"API Key 无效，去设置页检查"）。

验收模拟 401 与 429 → 分别显示对应提示；日志无凭证泄漏。

R4失败聚合横幅

工作台顶部持久横幅："N 段失败（图片 x · 配音 y · 提示词 z）"+ 一键重试 + 可展开失败清单定位分镜；分镜卡片同时展示多类错误而非只取第一个。数据源用现成 health + recovery.targets，基本无需后端改动。

验收计数正确、一键重试可用、刷新后横幅仍在；Playwright 截图。

R5部分失败可继续（不再一票否决）

失败项落库后任务不再整体中断，进入"带失败的可重试状态"；仅失败率超阈值（默认 >50%）或系统级错误（auth/config）才整体中断——那类失败重试也没用。改 task_executor.py:1235 与 :1555。

验收12 段 mock 2 段失败 → 其余完成、任务停在可重试态、R4 横幅出现。

R6前端静默轮询修复依赖 T3

三处手写轮询统一收编到现成的 usePolling/pollingSession（3 次连续失败 → 显式提示 + 退避）；预览轮询失败时清除"生成中"状态并给重试按钮。

验收轮询中关掉后端 → 数秒内出现"连接中断，点击重试"而非永久转圈。

R7finalize 失败循环

失败时附带具体缺失清单（build_resume_work 已能算出）；operation 记录连续失败次数，≥2 次时引导改走"重试缺失素材"。

R8后台巡检 sweeper

超时检测目前只在有人轮询时懒惰触发。加轻量后台线程（约 5 分钟一轮）跑 fail_stale_task_data() + 孤儿 operation 清理。

R9上传失败可见化

workspace 载荷为"Upload failed"情形输出 warning；前端以警示态 chip（"文件未入库"）展示并保留重试入口，不再伪装成功。

R10补齐重试 API

  • 新增 POST …/segments/{i}/regenerate-prompt，消除 needs_prompt 409 死胡同。
  • retry-assets 支持整片重配音通路（配合换音色）。
  • 同步 regenerate 接口加超时保护、失败写回 segment 状态；rebuild 异步化并加错误处理。

R11创建前就绪检查

新增 GET /config/readiness（llm/image/tts 各自 ready + 缺失项）；ManuscriptPage 提交前校验，未就绪弹 ConfirmDialog 引导跳设置页（保留"仍要继续"）。

Phase 2 · 用户引导 P1

G1阶段导航器 + 全局进度

复活死代码 TaskProgress.jsx 的加权进度模型，做成工作台顶部常驻步骤条：写文稿 → 生成预案 → 确认音色 → 确认画面 → 生成素材 → 完成；当前步高亮、附一句话说明、总体百分比与预计剩余时间。

G2统一术语表

先定表后改码：任务→项目，各种"预案"→预案，segment→分镜。全局替换 UI 文案，后端字段不动。

G3空状态与下一步指引

每个阶段的操作条固定回答"你在哪 + 下一步做什么"；空画布上营销轮播降级，主位改为三步流程引导卡；首次进工作台的一次性引导浮层。

G4Tooltip 补齐

工作台关键控件：生成策略、版本冲突、重试范围、stale 含义、"离开本页不会中断"等。

G5清理装饰性控件

删除"受众人群"下拉框（默认删除，避免假承诺），或接入真实参数。

G6危险操作统一确认

"重新拆分"与"删除克隆音色"从 window.confirm 换成 ConfirmDialog，写明后果。

G7错误文案规范

所有错误从"裸 detail"改为「发生了什么 + 怎么办」两段式，依托 R3 的 error_code，集中在 errorMessages.js 维护。
